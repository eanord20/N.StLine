# Отчёт независимого тестировщика 2 — производственный инженер

**Кандидат:** N.StLine 1.1.0 + незакоммиченные функции материалов/отчётов. HEAD `9408582`, ветка `feat/nstline-mvp`.
**Дата:** 2026-10-30. **Каталог:** `qa-focus-20261030/agent2`.
**Метод:** собственный harness `agent2/harness` (net8.0-windows, UseWPF), прямые ссылки на свежие DLL из `src/NStLine.App/bin/Release/net8.0-windows` (без ProjectReference, без пересборки общих bin/obj). Запуск через `dotnet test -c Release` в каталоге harness (исполнение произвольных бинарников заблокировано политикой — harness обёрнут в один xUnit-тест, вызывающий `Program.<Main>$` через reflection). Пакеты xunit 2.5.3 / Microsoft.NET.Test.Sdk 17.8.0 уже были в локальном NuGet-кэше проекта, новых пакетов не ставилось.
**Независимый оракул:** собственная реализация точного поиска на целых числах (масштаб ×100): генерация всех допустимых мультинаборов + DFS-мемоизация по вектору спроса → минимальное число заготовок. Плюс проверка каждой заготовки (сумма длин + N·рез ≤ длина, остаток ≥ 0, покрытие спроса по ID деталей, арифметика остатков/потерь/итогов).
**Файлы настроек/библиотеки:** только `agent2/data/` (инъекция путей в `MaterialsLibraryService`/`AppSettingsService`). Реальный LocalAppData, буфер обмена и App.OnStartup не затрагивались. UI не имитировался: проверялись реальные ViewModel/сервисы headless в STA-потоке.

## Scope «разные длины заготовок»
В модели один `LinearMaterial` = одна `StandardLength` + `CutWidth`; смешанные длины заготовок внутри одного материала не поддержаны (и не заявлены). Реально поддержанный смысл — несколько материалов с разными длинами в одном проекте: проверено в M01 (6000/k3 и 12000/k5 одновременно, каждая заготовка получила длину своего материала). Источник: `ProjectCuttingEngine.cs:49-55`.

## Замечание об оптимальности (не дефект)
Второй критерий «минимум суммарного остатка» математически пуст: при фиксированном числе заготовок `TotalRemainder = B·L − Σдеталей − N·K` — константа (потери на рез зависят только от общего числа деталей). Проверено в RunCase по всем задачам: фактический `TotalRemainder` всегда равен этой константе. Корректности не мешает, но «двухкритериальная оптимизация» в спецификации фактически сводится к одной.

## Дефекты

### QA2-01 — Профиль точного поиска «Deep» отсутствует (спецификация требует Fast/Balanced/Deep/Custom)
- **Категория:** соответствие спецификации / функциональность.
- **Серьезность:** Medium.
- **Версия:** кандидат 1.1.0, HEAD 9408582 + незакоммиченные изменения.
- **Предусловия:** спецификация `.specs/NStLine.MVP.Spec.md` §2.1 п.35 (рабочая копия) предписывает профили Fast (4 с/25 000), Balanced (30 с/100 000), **Deep (90 с/1 000 000)** и Custom.
- **Ввод/шаги:** headless-прогон `MainViewModel.SelectedExactProfileKey = "deep"` (harness, тест U07); статический просмотр `AppConstants.cs`, `CalculationSettingsViewModel.cs`, `CalculationSettingsWindow.xaml`.
- **Ожидаемое (источник):** ключ `deep` принимается, лимиты 90 с / 1 000 000 паттернов (спец §2.1).
- **Факт:** ключ игнорируется — остаётся `balanced` (30/100 000). В `AppConstants` нет `DeepCuttingOptions`; `MainViewModel.ExactProfiles` (MainViewModel.cs:29-33) содержит только fast/balanced; `CalculationSettingsViewModel.cs:26` допускает только `fast|balanced|custom`; в `CalculationSettingsWindow.xaml:16-17` только два пресета.
- **Независимый расчёт/расхождение:** не применимо (функциональный пробел).
- **Доказательства:** `evidence/results.txt` U07 (FAIL): `key=balanced t=30 pat=100000`; файлы/строки выше.
- **Частота:** всегда.
- **Влияние:** пользователь не может задать «глубокий» поиск, предусмотренный спецификацией; для тяжёлых задач доступен только ручной Custom. Существующие тесты `MainViewModelCalculationTests` (`DeepProfile_CannotBeSelectedAgain`, `LegacyDeepProfile_LoadsAsCustomWithoutLosingLimits`) кодируют удаление профиля — вероятно, осознанное решение, но спецификация не обновлена.
- **Причина-гипотеза:** профиль намеренно убран при hardening точного поиска (коммит defb2ec/460bf27), спец §2.1 п.35 не синхронизирована.
- **Уверенность:** высокая (функционально подтверждено + код + тесты).
- **Ограничения:** проверено на уровне VM/XAML/констант; через реальный диалог не кликалось (UI headless).

### QA2-02 — Итоговый «коэффициент использования» не включает потери на рез и расходится с примером спецификации
- **Категория:** корректность показателя / соответствие спецификации.
- **Серьезность:** Low.
- **Версия:** кандидат 1.1.0.
- **Предусловия:** любой расчёт с `CutWidth > 0`.
- **Ввод:** задача `5997×1`, заготовка 6000, рез 3 (тест T06); спец §9.1: строка `6000 | 3 | 2400+1800+1200 | ост.591 | 90.1%` — там «Использование» = (детали+пропил)/заготовка = 5409/6000 = 90.15%→90.1%.
- **Шаги:** `CuttingEngine.Solve` → `CuttingResult.UtilizationPercent` (harness T06; код `CuttingResult` вычисляется в солверах как `TotalPartLength/TotalBarLength`, `ExactPatternSolver.cs:426-428`, `FirstFitDecreasingSolver.cs:70-72`; `ProjectCuttingResult.cs:16` — то же).
- **Ожидаемое (источник):** по образцу спецификации использование учитывает пропил: для T06 это 100%.
- **Факт:** `util=99.95%` (= 5997/6000), пропил исключён. Дополнительно: в таблице заготовок `ResultPanel.xaml:76-87` нет колонки «Использование», предусмотренной спец §9.1.
- **Расхождение:** 0.05 п.п. на T06; на многообъектных задачах расхождение = TotalCutLoss/TotalBarLength (напр. T08: 91.46% vs 92.26%).
- **Доказательства:** `evidence/results.txt` T06 (`util=99,95%`), T03 (`util=80%` vs 80.13% с резом).
- **Частота:** всегда при K>0.
- **Влияние:** заниженный/иной КИМ относительно примера спецификации; потенциальная путаница (две разных методики в одном документе).
- **Причина-гипотеза:** метрика определена как «чистый металл»; спец §9.1 считает «использование заготовки» включая пропил.
- **Уверенность:** средняя-высокая (расчёт воспроизводим; трактовка спецификации двусмысленна).
- **Ограничения:** статика + расчёт агрегата; UI-колонка проверена по XAML.

### QA2-03 — Вставка из буфера: некорректное количество молча заменяется на 1 вместо пометки строки ошибкой
- **Категория:** валидация ввода / UX-честность.
- **Серьезность:** Low.
- **Версия:** кандидат 1.1.0.
- **Предусловия:** вставка строк вида `Имя<TAB>Длина<TAB>Количество`.
- **Ввод:** `D\t100\t0` и `D\t100\t-3` (harness P01); код `PartPasteParser.cs:55-75` (`Math.Max(1, quantity)`, округление `asDouble` AwayFromZero) и `MainViewModel.cs:664` (`Quantity = Math.Max(1, quantity)`).
- **Ожидаемое (источник):** спец §10.2: Quantity — целое > 0; §10.3: некорректные строки помечаются ошибкой.
- **Факт:** `0` и `-3` молча превращаются в `1` — дефект ввода невидим, заявка на 0 деталей становится заказом на 1.
- **Расхождение:** тихая модификация количества — нарушает принцип «Quantity is never altered» (AGENTS.md) на этапе ввода.
- **Доказательства:** `evidence/results.txt` P01: `qty0:True/1 qtyNeg:True/1`.
- **Частота:** всегда при таком вводе; дробное `2.7` также округляется до 3.
- **Влияние:** для производства риск лишней детали/неправильного набора.
- **Причина-гипотеза:** намеренный clamp «как в Excel», но без сигнала ошибки.
- **Уверенность:** высокая.
- **Ограничения:** проверен сам парсер (публичный API), не реальный Clipboard.
