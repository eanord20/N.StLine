# QA5 — Ввод деталей / вставка из Excel — отчёт тестировщика agent5

- Продукт: N.StLine 1.1.0 + uncommitted, HEAD 9408582, ветка feat/nstline-mvp
- Платформа: Windows 10.0.26300, .NET 8
- Метод: execution через harness `harness/PasteHarness.csproj` (прямые `<Reference>` на
  `src/NStLine.App/bin/Release/net8.0-windows/{NStLine.App,NStLine.Core,NStLine.Cutting}.dll`,
  без ProjectReference, без новых пакетов) + static analysis исходников.
- Доказательства: `parser-results.json` (172 запуска: 43 кейса × 4 культуры процесса),
  `vm-results.txt`, `inputs.txt`, `harness/`.

## Покрытый реальный формат вставки

Источник истины — код (`PartPasteParser.cs`, `MainViewModel.PasteFromClipboard` строки 638-688):
текст буфера → строки по `\r\n|\n|\r` (RemoveEmptyEntries) → ячейки по `\t` (Trim) →
1 ячейка = Length; 2 ячейки = Length+Qty если обе числовые, иначе Name+Length;
3+ ячеек = Name+Length+Qty (лишние столбцы игнорируются). Parse double: `NumberStyles.Float`
по `CurrentCulture`, затем fallback `InvariantCulture`. Спецификация:
`.specs/NStLine.Concept.md` §7, `.specs/NStLine.MVP.Spec.md` §10.3.

## Ограничения метода (BLOCKED)

- `PasteFromClipboard` читает `System.Windows.Clipboard` напрямую; изменять системный
  буфер запрещено заданием → реальный путь «Excel → Ctrl+V → кнопка Paste» НЕ выполнен,
  статус **BLOCKED**. Цикл вставки воспроизведён построчно по исходнику (строки 651-670)
  с вызовом реального `PartPasteParser`; единственная непроверенная часть — сам
  `Clipboard.GetText()` и `MessageBox` при полном провале.
- UI-клики не имитировались. `MainViewModel` создан в harness с внедренными
  fake-сервисами (без `App.OnStartup`, без AppData) — ручной ввод проверен
  execution-методом через публичный API VM.

## QA5-01 — Невалидные строки молча отбрасываются вместо пометки ошибкой

- Категория: обработка ошибок / соответствие спецификации
- Серьёзность: Major | Частота: всегда | Уверенность: высокая
- Версия: 1.1.0+uncommitted HEAD 9408582
- Предусловия: активный материал, буфер содержит смесь валидных/невалидных строк.
- Ввод: `"A\t100\t1\r\nB\tbad\t2\r\nC\t200\t2"` (P31), `"Стойка\tabc\t3"` (P13),
  `"Стойка"` (P30), `"Стойка\t1250 мм\t3"` (P29).
- Команда: `dotnet build -c Release -t:Run --no-incremental` в `harness/`.
- Ожидание (Concept §7.2, MVP §10.3): «некорректные помечаются ошибкой, но не блокируют
  остальные» — строка должна появиться в таблице с индикацией ошибки.
- Факт: `TryParse` вернул false → `continue` (MainViewModel.cs:655-656) — строка
  исчезает бесследно. P31: добавлены строки 1,3,4,5; строка 2 пропала. P13/P29/P30:
  добавлено 0 строк.
- Доказательства: parser-results.json P13, P29, P30, P31 (skippedLines).
- Влияние: пользователь теряет части заказа без уведомления; при ≥1 добавленной
  строке вообще нет сообщения.
- Предполагаемая причина: отсутствует механизм «добавить строку с ошибкой» —
  парсер возвращает bool, VM пропускает строку.
- Ограничения: пометка в UI проверена static; сам цикл — реплика.

## QA5-02 — Молчаливое изменение количества при вставке

- Категория: целостность данных | Серьёзность: Critical | Частота: всегда
- Предусловия: любые; ввод как ниже.
- Ввод и факт (все 4 культуры, parser-results.json):
  - `1200\t0` → qty **1** (P06)
  - `1200\t-3`, `Стойка\t1200\t-3` → qty **1** (P07, P07b)
  - `1250\t4.5` → qty **5**; `1250\t2.4` → qty **2**; `Стойка\t1250\t4.5` → **5** (P05*)
  - `500\t99999999999` → qty **1** (P22; double→int overflow → int.MinValue → Max(1,·))
  - `500\t3,5` @ru/uk/de → qty **4** (P40; @en строка отброшена — см. QA5-04)
- Ожидание (Concept §7.2, MVP §10.2): qty — целое >0; «отрицательное или нулевое
  значение → ошибка»; дробное/нецелое количество не должно округляться молча.
- Независимый расчёт расхождения: введённое 0/−3/4.5/1e11 ≠ записанное 1/1/5/1
  (абсолютные расхождения 1, 4, 0.5, ~1e11).
- Причина: `TryParseQuantity` (PartPasteParser.cs:55-75): `Math.Max(1, parsedInt)`,
  затем fallback `Math.Round(asDouble, AwayFromZero)` + `Math.Max(1,·)` — ветка
  спроектирована «всегда успешна» для любого числа.
- Замечание: при этом `MainViewModel.PasteFromClipboard` дополнительно делает
  `Math.Max(1, quantity)` (строка 664) — двойное принуждение.
- Влияние: неверное количество деталей в заказе без какого-либо признака —
  прямое нарушение правила AGENTS «Quantity is never altered by the algorithm»
  по духу (здесь меняет ввод).

## QA5-03 — Второй числовой столбец всегда трактуется как количество

- Категория: эвристика столбцов | Серьёзность: Major | Частота: всегда при
  двух числовых столбцах
- Ввод → факт:
  - `2400\t6000` → length=2400, qty=**6000** (P08) — если пользователь скопировал
    «длина детали, длина заготовки» или «длина, остаток» — создаётся 6000 деталей.
  - `1234\t1250` → length=1234, qty=**1250** (P27) — числовое имя невозможно.
- Ожидание: эвристика допустима по Concept §7.1, но без sanity-проверки
  (qty в разумных пределах, подтверждение) получается молчаливое раздувание заказа.
- Влияние: тысячи лишних деталей → неверный расчёт/зависание exact-солвера.
- Причина: PartPasteParser.cs:23-32 — приоритет «обе числовые = length+qty».

## QA5-04 — Итог вставки зависит от культуры процесса ОС

- Категория: локализация/культура | Серьёзность: Major | Частота: зависит от ОС
- Ввод `Стойка\t1250,5\t3` (P14):
  - @en-US → строка **отброшена** (skipped, paste failed message)
  - @ru-RU, uk-UA, de-DE → length=1250.5, qty=3
- Ввод `500\t3,5` (P40): @en-US → отброшена; @ru/uk/de → qty=4 (ещё и округление).
- Ожидание: детерминированность — одинаковый ввод → одинаковый результат
  (правило проекта «Identical input always produces identical output» для
  пользователя; UI-язык приложения en/ua не влияет на парсер — проверено:
  парсер использует `CultureInfo.CurrentCulture`, а не `_localization.Culture`).
- Влияние: один и тот же Excel-файл вставляется по-разному на разных ПК.
- Причина: PartPasteParser.cs:51-52 — двойной TryParse CurrentCulture||Invariant.
- Ограничение: язык локализации приложения проверен отдельно — он не участвует
  в разборе (ресурсы только строки).

## QA5-05 — «1.250» молча превращается в 1.25 мм

- Категория: целостность данных / культура | Серьёзность: Critical | Частота: всегда
- Ввод: `Стойка\t1.250\t2` (P16) → во **всех** культурах length=**1.25**, qty=2.
- Ожидание: для пользователя de/ru/uk, где «.» — разделитель разрядов или опечатка,
  «1.250» читается как 1250; минимум — неоднозначность должна помечаться.
- Факт: `NumberStyles.Float` запрещает group separator → de/ru/uk-парс падает →
  invariant-парс даёт 1.25. Строка добавляется, `ValidateRow` не видит ошибки
  (1.25 мм «валидна»), расчёт считает деталь длиной 1.25 мм.
- Точное расхождение: 1250 ожидаемо vs 1.25 фактически — в 1000 раз.
- Причина: invariant fallback без проверки неоднозначности формата.

## QA5-06 — Пустая ячейка количества отбрасывает всю строку

- Серьёзность: Medium | Ввод `Стойка\t1250\t` (P10, trailing TAB — типично при
  копировании из Excel диапазона с пустым 3-м столбцом) → строка отброшена во
  всех культурах; при единственной строке — «paste failed».
- Ожидание (Concept §7.2): «отсутствует количество → устанавливается 1 с пометкой».
- Факт: `TryParseQuantity("")` false → TryParse false → skip.
- Причина: отсутствует ветка «пустая ячейка qty → default 1» для ≥3 столбцов
  (ср. P11 `\t1250\t5` — пустое имя допустимо, пустое qty — нет: асимметрия).

## QA5-07 — Столбцы после третьего молча игнорируются

- Серьёзность: Medium | Ввод `Стойка\t1250\t10\tEXTRA` (P09) → добавлена
  корректная строка, 4-й столбец потерян без сообщения.
- Влияние: если пользователь копирует таблицу с материалом/примечанием —
  данные теряются молча; ни спека, ни UI не предупреждают.

## QA5-08 — Нет обратной связи о пропущенных строках при частичном успехе

- Серьёзность: Major | Static (MainViewModel.cs:672-680): `MessageBox` показывается
  только когда `Parts.Count == originalCount`; при N добавленных и M пропущенных
  пользователь не получает ни счётчика, ни списка строк. Exec-подтверждение:
  P31 addedRows=4, skippedLines=[2], wouldShowPasteFailed=false.
- Требование MVP §10.3 «некорректные помечаются» не выполнено ни пометкой,
  ни сообщением.

## QA5-09 — Эвристика 2-ячеек: «текст\tчисло» = Name+Length

- Серьёзность: Medium | Ввод → факт (en-US, то же в остальных):
  - `0x100\t2` → name="0x100", length=**2**, qty=1 (P35)
  - `A100\t2` → name="A100", length=**2**, qty=1 (P39)
  - `﻿1250\t2` (BOM) → name="﻿1250", length=**2**, qty=1 (P25)
  - `1250\tСтойка` → строка отброшена (P28)
- Ожидание: «A100\t2» правдоподобнее «имя + количество» (длина 2 мм бессмысленна),
  либо ошибка. BOM не снимается (Trim не удаляет U+FEFF — не whitespace).
- Влияние: появляются строки с длиной 2 мм, валидные для валидатора —
  мусор в расчёте без предупреждения.

## QA5-10 — Числа с разделителем разрядов отбрасываются

- Серьёзность: Medium | Ввод `Стойка\t1 250\t2` и `1 250` (NBSP) → skip во всех
  культурах (P17, P18). Excel-ячейки формата `# ##0` (типично для ru/fr/locale UA)
  копируются именно так → реальные пользовательские данные теряются.
- Причина: `NumberStyles.Float` не включает AllowThousands; NBSP вообще не
  является whitespace/разделителем для TryParse.

## QA5-11 — Длина ≤0 / NaN / Infinity: добавляется, но помечается

- Статус: PASS с замечанием | Ввод `-500\t2`, `0\t2`, `NaN\t2`, `Infinity\t2`
  → строки добавляются; execution через реальный VM (vm-results.txt):
  Length=0/-5 → «Length must be greater than zero», 5998 при баре 6000 и резе 3 →
  «Part does not fit into the bar». NaN также попадёт под ту же ошибку
  (ValidateRow: `!double.IsFinite`). Замечание: сообщение для NaN/Infinity
  текстуально неточно («greater than zero»), но строка помечается.

## QA5-12 — Расхождение ручного ввода и вставки

- Серьёзность: Major | Exec (vm-results.txt + replicant):
  - Ручной ввод qty=0 → ошибка «Quantity must be greater than zero», значение
    остаётся 0, строка помечена. Вставка `1200\t0` → qty молча 1, без ошибки.
  - Ручной ввод qty=−3 → ошибка; вставка `-3` → qty 1 без ошибки.
  - Ручной ввод длины «1250,5»: @en-US binding FAIL (ArgumentException —
    значение не меняется), @ru-RU → 1250.5. Вставка принимает обе формы
    (fallback), т.е. вставка шире ручного ввода, но культура-зависима (QA5-04).
  - Ручной ввод «1 250», «abc» → binding FAIL (молча остаётся старое значение —
    стандартное поведение WPF, отдельное наблюдение).
  - `ReplaceQuantityFromKeyboard(0)` → qty=0 + ошибка — клавиша «0» ставит
    некорректное значение без защиты (UI-путь MainWindow.xaml.cs:39-62
    допускает любую цифру).
- Требование: единая семантика значения независимо от способа ввода — нарушена.

## QA5-13 — Реальный путь Excel/буфер обмена

- Статус: **BLOCKED**. `Clipboard.SetText` меняет системный буфер — запрещено;
  `PasteFromClipboard` приватный и читает Clipboard напрямую (нет инъекции
  источника текста). Реальный Excel не использовался. Проверено: реальный
  `PartPasteParser` (Release DLL) + verbatim-реплика цикла строк 651-670.
  Непроверенное: Clipboard.GetText/ContainsText, MessageBox при полном провале,
  CanExecute (`ActiveMaterialId != null`).

## QA5-14 — Корректные сценарии (PASS)

- Дубли `A\t100\t1` ×2 → обе строки (P32) — допустимо.
- Пустые/whitespace строки пропускаются, смешанные CRLF/CR/LF — корректно
  (P12, P33).
- `500\t+3` → qty 3 (P34); `1e3\t2` → 1000 (P19) — формально ок, хотя
  экспонента в поле длины — спорно, но детерминировано.
- Автоимена `Part N` при пустом имени (P01, P11).
- Моноколоночный текст `Стойка` → skip + сообщение при полном провале (P30) —
  соответствует MVP §10.3 «показывается сообщение».

## QA5-15 — Граничная длина относительно заготовки (PASS, exec)

- Материал 6000/рез 3: Length=5997 → ошибок нет; 5998 → «Part does not fit
  into the bar» — правило `Length + CutWidth <= StandardLength` соблюдено.

## Общие примечания

- `PasteFromClipboard` требует `ActiveMaterialId` — без активного материала
  вставка молча ничего не делает (CanExecute должен блокировать кнопку; static).
- Все вставленные строки получают активный материал; материал из буфера
  не распознаётся (связано с QA5-07).
- Процессная культура ≠ язык приложения: `LocalizationService.Culture` —
  отдельная строковая таблица, на парсинг не влияет (static + код).
