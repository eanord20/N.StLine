## Методологическая оговорка (ограничение, не дефект)

Фоновые агенты имели запрет запуска произвольных exe. Обходы:
- agent2 — harness обёрнут в xUnit-тест (`dotnet test`);
- agent4 — custom MSBuild target (`dotnet build -t:Run`);
- agent5 — `dotnet build -t:Run`;
- agent3 и agent6 — выполнены foreground-координатором (`evidence-rerun.json`,
  `suite-evidence.txt`, `cancel-evidence.txt` — подтверждены, exit 0).
Это ограничение управления разрешениями/методики, а не обход политики продукта.
Полной независимости экспериментов нет: отдельные контексты, но общий filesystem/machine/модель.
Evidence-качество у agent3/agent6/agent4 наивысшее (полные входы в JSON); у agent1/agent2/agent5
также записаны факты, но часть VM-путей — реплика кода, не исполнение.

## A. Консолидированный каталог дефектов (execution-backed)

### D1. Ложный `Optimal` на десятичных длинах — ПОДТВЕРЖДЁН, High (я поднимаю до **Critical-кандидата**)

- Источники: QA6-01. Подтверждено независимым целочисленным oracle на 3000 задач
  (шаг 0.1 мм): 3 mismatch (caseIndex 1791/1876/2986) + ручной `decimal-ffd-trap`.
- Механизм проверен аудитором в коде: `ExactPatternSolver.cs:137`
  `maxCount = (int)Math.Floor(available/denominator)` без ε-компенсации — ветка с допустимым
  количеством теряется (напр. 0.7+0.7+0.9 в бар 2.3: `1.4/0.7=1.9999999999999998` → floor 1).
  Паттерн отсутствует → точный поиск «исчерпывает» усечённое пространство →
  `CuttingEngine.cs:42-46` или `ExactPatternSolver.cs:92-94` выдаёт `Optimal` на неминимуме.
- Воспроизводимость: `dotnet qa-focus-20261030\agent6\bin\Release\net8.0-windows\Harness.dll`
  (уже собран, команда для foreground). Полные входы в `suite-evidence.txt:407-853`.
- Сопоставление с agent4/agent3: **не противоречие**. Oracle agent4 — целые мм и малые
  задачи (FP-деление целых, делящихся нацело, точно) → 0 mismatches ожидаемо. Oracle agent3 —
  147 decimal-задач, проверял только count/геометрию (не статус, не multiset);
  при частоте ~0.1% ожидание — 0.15 случая. Матрицы разные, выводы совместимы.
- Практический масштаб: реальные доли мм (0.7, 0.9, 2.3) — это **не экзотика**,
  в отличие от 1e-10/1e308. Главный контракт продукта «Optimal = доказанный минимум» нарушен.
  Частота на целых мм не оценена (гипотеза аудитора: ~0, см. план R2).

### D2. Ложное отклонение десятичных допустимых деталей — ПОДТВЕРЖДЁН, **Medium-High**

- Источник: QA3-06 (3/150 входов с `Length+CutWidth == BarLength` в десятичном смысле:
  1.3+0.1 в 1.4; 0.4+0.2 в 0.6; полные входы в `evidence-rerun.json:706-757`).
- Код подтверждён: `CuttingEngine.cs:142` строгое `>` без допуска; тот же строгий
  контракт в `MainViewModel.cs:708` (`ValidateRow`) → пользователь видит «Part does not fit»
  на реалистичном вводе 0.1-мм точности. Спек §10.2 допускает равенство.
- Это входы **реального масштаба** — практически важнее, чем микродлины.
- Спорность: API тип double формально прав (1.3+0.1 > 1.4 в binary64); но пользователь
  мыслит decimal-мм → дефект UX/корректности, а не нарушение семантики double.

### D3. Абсолютный ε в FFD принимает переполненный бар + ложный Optimal — ПОДТВЕРЖДЁН, **Low (масштаб)**

- Источники: QA3-04 = QA6-02 (дубликаты, объединены). Вход: bar 1e-10, деталь 6e-11 ×2 →
  Optimal/1 bar/remainder −2e-11/120%. Код: `FirstFitDecreasingSolver.cs:115`
  `newUsedLength <= Length + 1e-9` — ε больше ёмкости; incumbent не перевалидируется.
- Спорность severity: на реальных мм переполнение ≤1e-9 мм — косметика; дефект класса
  «нет scale-aware сравнений», но практический вред минимален. Оставить **Low**.
- Сопутствующее: неклампленный remainder −5.6e-17 и util 100.00000000000003%
  (QA6 `decimal-exact`, `FirstFitDecreasingSolver.cs:49` — remainder без clamp).

### D4. Молчаливая подмена количества при вставке — ПОДТВЕРЖДЁН, **Major**

- Источники: QA1-04, QA2-03, QA3-01, часть QA5-02 (четырёхкратное независимое
  подтверждение, обе культуры). Факты: qty `0→1`, `-3→1`, `2.5→3`, `4.5→5`,
  `2147483648→1`, `1e100→1`, `Infinity→1` (`PartPasteParser.cs:55-75` +
  двойной `Math.Max(1,·)` в `MainViewModel.cs:664`).
- Спек-основание: Concept §7.2 «отрицательное или нулевое → ошибка» — нарушено.
- Аудиторская градация severity: **Major** (не Critical): путь только через вставку,
  результат виден в таблице. Дробное округление (2.5→3) — спорная подчасть:
  Concept требует ошибку только для ≤0/текста; для дробного требования нет →
  округление — Disputed (см. C5). Нецелые/переполненные double→int (1e11→1) — явный дефект.

### D5. Невалидные строки вставки молча отбрасываются — ПОДТВЕРЖДЁН, **Major**

- Источник: QA5-01 + QA5-08 (+ частично QA1 observation). `MainViewModel.cs:655-656`

  QA5-10 (`"1 250"`/NBSP — реальные Excel-данные теряются, Medium).

### D6. Битый JSON собственных файлов → необрабатываемое исключение — ПОДТВЕРЖДЁН, **Major**

- Источники: QA1-02 (materials.json) + QA1-03 (settings.json) — объединены в один

### D7. Битый `.nstline` → необрабатываемое исключение → **завершение процесса**

- Severity повышена: **Major** (было Minor у agent1).

### D8. Сброс stale при публикации результата после правки во время расчёта — VM-ПОДТВЕРЖДЁН, **Medium-High**

- Источник: QA3-02 (gate-сценарий: edit во время Solve → `IsCurrentResultStale=false`,
  `copyEnabled=true`, evidence `evidence-rerun.json:849-858`).
- Код подтверждён: `SetCurrentResult` безусловно `IsCurrentResultStale=false`
  (`MainViewModel.cs:778`); `MarkCurrentResultStale` сработавший во время busy
  перетирается при публикации. Спек §8.3 требует блокировку Copy/Report до пересчёта.
- Desktop-достижимость: PartsGrid не имеет `IsEnabled/IsReadOnly` от `IsBusy`
  (проверено `MainWindow.xaml:234-339`) → правка во время расчёта реально возможна
  (статическое подтверждение; живой desktop-прогон не выполнялся).

### D9. Переполнение `+` количества int.MaxValue → отрицательное — VM-ПОДТВЕРЖДЁН, **Low-Medium**

- Источник: QA3-03. `row.Quantity++` без проверки (`MainViewModel.cs:567`).
  Достижимо только ручным вводом 2147483647 → Low-Medium.

### D10. NRE на null-элементе Parts — ПОДТВЕРЖДЁН, **Minor (API-only)**

- Источники: QA4-X1 = QA6-05a (дубликат). `CuttingEngine.cs:133-134` делает `continue`
  для null, затем `ExactPatternSolver` ctor (`:36-40`) и FFD (`:9-14`) падают NRE.
  Недостижимо из UI (строки не бывают null).

### D11. Cancel игнорируется во время FFD (~810 мс) — ПОДТВЕРЖДЁН, **Medium-Low**

- Источник: QA6-03, измерено в дочернем процессе (cancel-evidence.txt: delayAfterCancel=810ms,
  peak 44.7MB). Причина: токен проверяется до FFD (`CuttingEngine.cs:14,18`), FFD его не получает.
  Масштаб O(n·bars). Состояние после отмены корректно (retry PASS).

### D12. Переполнение агрегатов → Infinity/NaN/0 в итогах — ПОДТВЕРЖДЁН, **Low**

- Источники: QA3-05 = QA6-04 (дубликат; util=0 при 6e307×2 / NaN при 9e307×2,
  `TotalBarLength=Infinity`). `FirstFitDecreasingSolver.cs:70-72`,
  `ExactPatternSolver.cs:426-428`, `CuttingResult` суммы без проверки.
  Нереалистичный масштаб; статус Optimal на нечисловых итогах — честность нарушена формально.

### D13. `floor→int` переполнение → необъяснимый `BestFound` — ПОДТВЕРЖДЁН, **Medium-Low**

- Источник: QA6-05b. `BarLength=6000, part=1e-6, qty=2` → `BestFound/ExactNotCompleted`,
  `GeneratedPatterns=0`. Механизм: `ExactPatternSolver.cs:137` `(int)Math.Floor(≈6e9)`
  → int.MinValue → maxCount=0 → ни одного паттерна; `Solve():75-76` → null →
  `CuttingEngine.cs:42-56` → BestFound (не Optimal — «честная» сторона,
  но статус и причина не объясняют отказ на тривиальной задаче).

### C2. Формула utilization (QA2-02) — **реальная несогласованность со спеком, Low-Medium**

- Вердикт: спек-несоответствие подтверждено (пример содержит числа — не двусмысленность,
  а расхождение), но влияние информационное → **Low-Medium**. Включить в R2 проверку
  согласованности DOCX (там та же формула? — не проверено ни одним агентом).

### C3. «1.250» → 1.25 (QA5-05 Critical) — **Disputed, аудитор снижает до Medium**

- Факт подтверждён кодом (`PartPasteParser.cs:51-52`, Float не допускает group-sep →
  invariant даёт 1.25). Но: строка «1.250» семантически неоднозначна; для en-US-пользователя
  1.25 — корректное чтение; спек не требует обработки разделителей разрядов.
  Локали приложения — только EN/UA; в UA формальный разделитель разрядов — пробел/NBSP,
  не точка → 1000×-искажение возможно только при ошибочном вводе самим пользователем.
- Вердикт: **Disputed/Medium** — молчаливая неоднозначность (нет признака «не уверен»)
  заслуживает пометки, но Critical не оправдан. Не считать доказанным дефектом.

### C4. Два числовых столбца = длина+количество (QA5-03 Major) — **соответствует спецификации**

- Concept §7.1:162 **явно предписывает**: два числовых столбца = длина и количество.
  `2400\t6000`→qty 6000 — это задокументированное поведение, а не баг.
- Вердикт: не дефект продукта; риск раздувания заказа — слабость дизайна спеки
  (нет sanity-cap). **Info/spec-risk**, предложить обсудить порог/подтверждение.

### C5. Дробное количество округляется (часть D4) — **Disputed**

- `2.5→3`, `4.5→5`: Concept §7.2 требует ошибку для ≤0 и текста; для дробного

  как факт, но классифицировать отдельно: **Disputed-Low**.

### C6. «текст\tчисло» → имя+длина (QA5-09) — **Disputed/Info**

- Спек §7.1 покрывает только два числовых и три столбца; трактовка name+length
  правдоподобна, но даёт мусорные длины («A100\t2» → 2 мм). Не регламентировано → Info.

### C7. Культуро-зависимость вставки (QA5-04 Major) — **Medium**
