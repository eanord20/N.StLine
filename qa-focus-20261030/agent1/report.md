## Дефекты

### QA1-01. Отсутствует профиль точного поиска «Deep» (90 с, 1 000 000 паттернов)

- **Категория:** функциональность / соответствие спецификации
- **Серьёзность:** Major
- **Версия:** 1.1.0 + uncommitted, HEAD 9408582
- **Предусловия:** приложение запущено, открыть Edit → Calculation settings.
- **Ввод/шаги:** программно `vm.SelectedExactProfileKey = "deep"`; `new CalculationSettingsViewModel("balanced",30,100000).SelectedExactProfileKey = "deep"`.
- **Ожидание (источник):** `.specs/NStLine.MVP.Spec.md` §2.1 (строка 35): «профили Fast (4 с, 25 000), Balanced (30 с, 100 000, по умолчанию), Deep (90 с, 1 000 000) и Custom».
- **Факт:** значение «deep» отклоняется обоими VM (`MainViewModel.ExactProfiles` содержит только fast/balanced, `CalculationSettingsViewModel` допускает `fast|balanced|custom`); в `CalculationSettingsWindow.xaml` (строки 16–18) только три ComboBoxItem — пункта Deep нет. После присваивания ключ остаётся прежним (`fast 4/25000`, `balanced`). Deep (90 с/1 000 000) недоступен.
- **Доказательства:** `evidence/results.json` S6 «deep profile accepted» pass=false (actual `fast 4/25000`), «settings dialog deep» pass=false (actual `balanced`). Код: `src/NStLine.App/ViewModels/MainViewModel.cs:29-33`, `CalculationSettingsViewModel.cs:26`, `Views/CalculationSettingsWindow.xaml:16-18`, `src/NStLine.Core/Constants/AppConstants.cs:22-34` (нет DeepCuttingOptions).
- **Частота:** 100%.
- **Влияние:** документированный пресет недоступен; пользователь может вручную ввести 90/1 000 000 через Custom (обход есть), но по дефолту глубокий поиск не выбрать.
- **Предполагаемая причина:** Deep просто не добавлен в `ExactProfiles`/константы/XAML при изменении спецификации.
- **Уверенность:** высокая.
- **Ограничения:** проверено на уровне VM/XAML; то же видно статически в разметке.

### QA1-02. Повреждённый `materials.json` приводит к необрабатываемому исключению при старте

- **Категория:** обработка ошибок / запуск
- **Серьёзность:** Major
- **Версия:** 1.1.0 + uncommitted
- **Предусловия:** файл библиотеки материалов существует, но содержит невалидный JSON.
- **Ввод/шаги:** `File.WriteAllText(materials.json, "{ this is not json !!!")`; `new MaterialsLibraryService(path).LoadAll()` — либо конструктор `MainViewModel` (вызывает `LoadLibrary()` → `LoadAll()`).
- **Ожидание (источник):** здравый смысл/UX — приложение должно стартовать с пустой библиотекой или показать понятную ошибку; AGENTS/spec требуют «честного статуса», не падения.
- **Факт:** `System.Text.Json.JsonException` пробрасывается без обработки из `LoadAll` (`MaterialsLibraryService.cs:23-28` — нет try/catch и нет `Validate` при загрузке собственного файла). В штатном приложении это происходит в конструкторе `MainViewModel` из `App.OnStartup` → приложение не запускается (exception до `mainWindow.Show()`).
- **Доказательства:** `results.json` S1 «corrupt materials.json»: `unhandled JsonException: The JSON value could not be converted... BytePositionInLine: 1`.
- **Частота:** 100% при битом файле.
- **Влияние:** единственный битый файл данных делает приложение незапускаемым; данные библиотеки теряются без сообщения.
- **Предполагаемая причина:** отсутствует обработка ошибок десериализации в `LoadAll`.
- **Уверенность:** высокая.
- **Ограничения:** воспроизведено на сервисе напрямую; цепочка до старта приложения — по коду (MainViewModel.ctor:121 `LoadLibrary()`).

### QA1-04. Вставка из буфера молча искажает количество деталей

- **Категория:** корректность ввода / понятность UI
- **Серьёзность:** Minor
- **Версия:** 1.1.0 + uncommitted
- **Предусловия:** активный материал, вставка строк табулятором (анализ парсера; сам буфер не трогался).
- **Ввод/шаги:** `PartPasteParser.TryParse` для `"Shelf\t1500\t-5"`, `"Shelf\t1500\t0"`, `"Shelf\t1500\t2.5"`.
- **Ожидание (источник):** спецификация требует «валидацию строк с индикацией ошибок» и детерминизм; инженер ожидает либо отказ строки, либо точное значение — не молчаливую замену.
- **Факт:** `qty "-5" → 1`, `qty "0" → 1`, `qty "2.5" → 3` (округление AwayFromZero) — строка вставляется, ошибок нет (`PartPasteParser.cs:58-70`). Дополнительно две ячейки `"Name\t3"` трактуются как имя+длина=3 мм, а не имя+количество.
- **Доказательства:** `results.json` S4: `qty -5 → qty=1 ok=True`, `2.5 → qty=3`, `0 → qty=1`, `Shelf\t3 → len=3`.
- **Частота:** 100% для такого ввода.
- **Влияние:** реальный заказ (например «2.5» из Excel-формулы) молча превращается в другое количество → неправильный раскрой; ошибку можно заметить только визуально в таблице.
- **Предполагаемая причина:** `Math.Max(1, ...)` и `Round` в `TryParseQuantity` — решение «исправлять, а не отвергать» без индикации.
- **Уверенность:** высокая в факте; средняя в классификации как дефект (возможное осознанное решение).
- **Ограничения:** проверен парсер, а не реальный Ctrl+V (буфер не трогался по требованиям).

### QA1-05. Открытие повреждённого `.nstline` — сырое исключение без понятного сообщения

- **Категория:** обработка ошибок / UX
- **Серьёзность:** Minor
- **Версия:** 1.1.0 + uncommitted
- **Предусловия:** выбрать битый файл проекта через File → Open project.
- **Ввод/шаги:** `ProjectFileService.Load("bad.nstline")` с содержимым `"{{{"`.
- **Ожидание (источник):** понятное пользователю сообщение (как `MessagePasteFailed`).
- **Факт:** `JsonException` вылетает из `Load`; `MainViewModel.OpenProject` (MainViewModel.cs:998-1015) не имеет try/catch — исключение уходит в `DispatcherUnhandledException`, пишется в crash.log, статусная строка не обновляется: пользователь видит «ничего не произошло».
- **Доказательства:** `results.json` S8 «corrupt project» — JsonException; код `MainViewModel.cs:998-1015` (сравнить с `PasteFromClipboard`:684-687 — там MessageBox).
- **Частота:** 100% при битом файле.
- **Влияние:** приложение не падает (перехват на уровне App), но пользователь не понимает причину.
- **Предполагаемая причина:** пропущен try/catch в `OpenProject`/`SaveProject`.
- **Уверенность:** высокая.

## Наблюдения (не оформлены как дефекты)

- Частично неудачная вставка: нечитаемые строки молча пропускаются (`continue`), предупреждение только если не добавлено ни одной строки (`MainViewModel.cs:655,672-680`). Строки с ошибками валидации всё равно подсвечиваются — частично смягчает.
- `ClearAll` стирает задачу и историю Undo без подтверждения (`MainViewModel.cs:957-967`). Спецификация не требует подтверждения — зарегистрировано как UX-риск.
- Автоимя отчёта с точностью до секунды: два отчёта в одну секунду → одно имя, покрывается диалогом подтверждения замены.
- `SetActiveMaterial` допускает поиск по имени при неоднозначных именах (берётся первый) — потенциальная неоднозначность, сценарий маловероятен.

## Подтверждённое поведение (PASS, выборочно)

- Валидация строк: деталь > заготовки, length==bar при kerf>0 (по модели N деталей→N резов), qty≤0, отсутствие материала — корректные локализованные ошибки; Calculate заблокирован при ошибках.
- Расчёт: реальный движок — 2 заготовки минимально, `CutLoss=18` (6×3 мм) по модели спецификации, статус `Optimal`; повторный расчёт дал побайтово идентичные схемы (детерминизм подтверждён исполнением); при `MaxPatternCount=1` — честный `BestFound` с причиной «pattern limit».
- После правки результат помечается stale, Copy/Report блокируются — как требует спецификация.
- Undo восстанавливает добавление/удаление/редактирование; на границе `CanExecute=false`.
- Проект .nstline round-trip + легаси-миграция (MaterialId подставляется при единственном материале); `VM.LoadProject` (reflection) корректно наполняет задачу.
- Отчёт DOCX реально создаётся (файл 7 КБ), `LastReportPath` трекается; при отказе в подтверждении файл не перезаписывается; `ReportFileNameFormatter`: auto-имя, префикс/суффикс, `.docx` не дублируется, `CON`/`a<b`/300 символов — локализованный `ArgumentException`.
- Локализация EN/UA отличается и работает (`Оптимальне рішення|Розрахувати`); «ru» откатывается на EN.
- Реальные окна `MainWindow`, `CalculationSettingsWindow`, `MaterialsWindow` загружаются (XAML, app-ресурсы), `MainWindow.Measure` без исключений, `Show()` успешен — т.е. разметка/стили в Release DLL валидны.
- Импорт библиотеки: дедуп по нормализованному имени (Added=2/Skipped=1), конфликт Id получает новый Id, битый набор отклоняется целиком `InvalidDataException`.
