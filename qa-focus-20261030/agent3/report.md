## QA3-01 — Молчаливая подмена недопустимого количества при парсинге

- **Статус:** подтверждено на parser API; не desktop UI.
- **Категория:** ввод / целостность спроса. **Серьезность:** High.
- **Версия:** 1.1.0+uncommitted, HEAD9408582 по baseline, готовые Release DLL.
- **Предусловия:** вызов реального PartPasteParser.TryParse; отдельно культуры en-US и uk-UA; clipboard не используется.
- **Вход полностью:** для каждой культуры cells `["P","1000","0"]`, `["P","1000","-7"]`, `["P","1000","1.5"]`, `["P","1000","0.1"]`, `["P","1000","2147483648"]`, `["P","1000","1e100"]`, `["P","1000","Infinity"]`; дополнительно `["1250","1.5"]`.
- **Шаги/команда:** из agent3 `dotnet bin/Release/net8.0-windows/Harness.dll`; в первом child метод Parser(), для каждого массива записаны ok/name/length/quantity. Исходный запуск foreground-координатором, не этим фоновым агентом.
- **Ожидаемое с источником:** количество — целое >0 (spec `.specs/NStLine.MVP.Spec.md:355–358`), ошибочная строка должна быть обозначена ошибкой, не менять спрос (строки 362–365; проектный AGENTS: quantity never altered). Не объявляется обязательным конкретный текст ошибки; недопустима тихая подмена.
- **Факт:** для всех перечисленных трехколоночных массивов ok=true, Length=1000. Quantity 0→1, -7→1, 1.5→2, 0.1→1, 2147483648→1, 1e100→1, Infinity→1. `["1250","1.5"]` дает Length=1250, Quantity=2. Результаты одинаковы в обеих культурах.
- **Доказательства:** `evidence.json:2–106,136–148,249–353,383–395`; `src/NStLine.App/Services/PartPasteParser.cs:55–71`. Paste использует parser и Math.Max в `MainViewModel.cs:654–669` — это статическое подтверждение downstream-пути, не выполненный clipboard test.
- **Частота:** два запуска с одинаковым результатом; в каждом 14/14 трехколоночных вызовов подтвердили подмену (7 значений × 2 культуры), плюс 2/2 двухколоночных. Повтор: `evidence-rerun.json` те же диапазоны строк.
- **Влияние:** потенциально расчет/отчет внешне правдоподобен, но выполнен не для введенного спроса; после нормализации исходное ошибочное значение потеряно.
- **Причина-гипотеза:** Math.Max для целых, Round + unchecked double→int + Math.Max для прочих числовых значений вместо валидации.
- **Уверенность:** высокая для API; desktop-путь не подтвержден.
- **Ограничения:** не тестировалась фактическая вставка. Двухколоночная неоднозначность не выделяется как отдельный дефект. Name/length parsing не означает, что строка с NaN length пройдет VM validation.

## QA3-03 — Команда + переполняет положительное количество в отрицательное

- **Статус:** подтверждено на реальном VM, не desktop UI.
- **Категория:** VM / Int32 boundary. **Серьезность:** Medium.
- **Версия:** тот же кандидат 1.1.0+uncommitted / HEAD9408582.
- **Предусловия:** VM с in-memory сервисами; огромный спрос не отправляется solver.
- **Вход полностью:** материал Id=m, Name=M, StandardLength=6000, CutWidth=3; строка Part 1, MaterialId=m, Length=1000, Quantity=2147483647; один IncreaseQuantityCommand.Execute(row).
- **Шаги/команда:** общая команда; Vm(): присвоить int.MaxValue, Execute(+), записать Quantity/Error; вернуть Quantity=1 перед дальнейшим расчетом.
- **Ожидаемое с источником:** spec строка 357 — количество целое положительное; не превращать положительное значение в отрицательное (конкретный UX верхней границы не задан; нормальный вариант — не выполнять +).
- **Факт:** actual Quantity=**-2147483648**, Error="Quantity must be greater than zero.". Независимая арифметика: 2147483647+1=2147483648, не представимо Int32; сохраненное отрицательное значение отличается на -4294967296 от математической суммы.
- **Доказательства:** `evidence-rerun.json:826–833`; `MainViewModel.cs:560–568`; validation 706–707.
- **Частота:** 1/1 VM-вызов.
- **Влияние:** положительный спрос становится отрицательным; строка получает ошибку вместо безопасной обработки границы. Неверный solver-result не заявляется.
- **Причина-гипотеза:** незащищенный row.Quantity++ без верхней проверки Int32.
- **Уверенность:** высокая для VM-факта.
- **Ограничения:** ввод int.MaxValue через DataGrid и реальная UI-кнопка не проверялись; API команды выполнялся непосредственно; solver с huge quantity не запускался.

## QA3-04 — Непомещающиеся детали возвращены в одном баре со статусом Optimal

- **Статус:** подтверждено на engine API.
- **Категория:** математика / геометрическая допустимость / честность статуса. **Серьезность:** High, краевой масштаб ввода.
- **Версия:** тот же кандидат.
- **Предусловия:** прямой CuttingEngine.Solve, стандартные CuttingOptions, child под watchdog; всего две копии.
- **Вход полностью:** A: Material Id=m, Name=M, StandardLength=BarLength=1e-10, CutWidth=0; Part Id=p0, Name=P0, MaterialId=m, Length=6e-11, Quantity=2. B: те же идентификаторы, StandardLength=BarLength=1, CutWidth=0, Length=0.5000000002, Quantity=2. Options: TimeLimitSeconds=30, MaxPatternCount=100000, ToleranceMm=0.01.
- **Шаги/команда:** общая команда; Engine() случаи tiny / nearFit; записаны status, count, remainder, utilization и actualUsed каждого бара.
- **Ожидаемое с источником:** spec строки 215–219: сумма длин + рез ≤ bar; строки 243–251: отрицательный remainder недопустим. Независимая точная десятичная арифметика A: 2×0.00000000006=0.00000000012 >0.0000000001, превышение **0.00000000002 mm (20%)**; оптимум **2 bars**, суммарный остаток **0.00000000008 mm**. B: 2×0.5000000002=1.0000000004 >1, превышение **0.0000000004 mm**; оптимум **2 bars**, суммарный остаток **0.9999999996 mm**.
- **Факт:** A: Optimal, **1 bar**, actualUsed=1.2e-10, remainder=-1.9999999999999996e-11, utilization=120%. B: Optimal, **1 bar**, actualUsed=1.0000000004, remainder=-4.000000330961484e-10, utilization=100.00000004%. В обоих случаях баров **на 1 меньше допустимого оптимума**. Разница actual total remainder против математически допустимого 2-bar optimum: A около -1e-10 mm, B около -1 mm (суммарный остаток меняется вместе с числом баров).
- **Доказательства:** `evidence.json:588–643`; `FirstFitDecreasingSolver.cs:109–120` разрешает used<=Length+1e-9; result remainder 45–57; `CuttingEngine.cs:40–46` помечает heuristic incumbent Optimal при SearchCompleted.
- **Частота:** 2/2 на каждом из двух входов, два запуска; `evidence-rerun.json:588–643` повторяет исходный результат.
- **Влияние:** физически недопустимая схема с заявленным доказанным оптимумом. Особенно A нельзя объяснить только малой относительной ошибкой: 20% переполнения.
- **Причина-гипотеза:** абсолютный epsilon в FFD допускает геометрически неверный incumbent, затем доказательство не перепроверяет допустимость incumbent.
- **Уверенность:** высокая для API-факта и арифметики.
- **Ограничения:** ToleranceMm=0.01 указан в модели spec, но политика разрешения отрицательного остатка не оговорена и §7.4 прямо запрещает его. Для B практическое влияние ничтожно по абсолютной величине. UI может округлять/иначе валидировать такие значения; не проверено. Исправления продукта не делались.

## QA3-05 — Конечные размеры дают Infinity общей длины и ложные 0% использования

- **Статус:** подтверждено на engine API.
- **Категория:** numeric robustness / сводные метрики. **Серьезность:** Medium (нереалистичный масштаб).
- **Версия:** тот же кандидат.
- **Предусловия:** прямой CuttingEngine.Solve, два экземпляра детали, child под watchdog.
- **Вход полностью:** Material Id=m, Name=M, StandardLength=BarLength=1e308, CutWidth=0; Part Id=p0, MaterialId=m, Name=P0, Length=6e307, Quantity=2; CuttingOptions defaults 30 s / 100000 patterns / tolerance 0.01.
- **Шаги/команда:** общая команда; Engine() hugeFinite; получить count/total lengths/remainder/utilization.
- **Ожидаемое с источником:** spec §10.1–10.2 строки 348–358 разрешает конечные положительные входные размеры; §7.4 задает баланс; spec §1 строка 12 требует коэффициент использования. Независимая арифметика: 2 bars, total bars=2e308 (не помещается double), parts=1.2e308, remainder=8e307, utilization=(1.2e308/2e308)×100=**60%**. Если диапазон не поддерживается, требуется честное ограничение, а не неверная метрика.
- **Факт:** Optimal, count=2 (верно), TotalPartLength=1.2e308, TotalRemainder=8.000000000000001e307, **TotalBarLength=Infinity**, **UtilizationPercent=0**. Ошибка использования **-60 процентных пунктов**; распределение самих деталей корректно.
- **Доказательства:** `evidence.json:644–677`; `FirstFitDecreasingSolver.cs:70–72` деление агрегатов.
- **Частота:** 2/2, два запуска; `evidence-rerun.json:644–677` повторяет исходный результат.
- **Влияние:** неверная сводная метрика без ошибки при формально разрешенном конечном вводе; возможные downstream-проблемы вывода/сериализации не тестировались и не утверждаются.
- **Причина-гипотеза:** переполнение суммарной длины double; конечный числитель / Infinity дает 0.
- **Уверенность:** высокая на API; desktop-достижимость не проверена.
- **Ограничения:** физически нереалистичные размеры; spec не ограничивает прикладной диапазон. Сам count и per-bar геометрия верны. Это не OOM и не ошибка watchdog.

## QA3-06 — Граничные десятичные детали ошибочно отвергаются как непомещающиеся

- **Статус:** подтверждено на engine API относительно десятичных размеров пользователя; 3 INPUT+исключение, не PASS.
- **Категория:** числовая валидация / дробные миллиметры. **Серьезность:** Medium.
- **Версия:** тот же кандидат 1.1.0+uncommitted / HEAD9408582.
- **Предусловия:** реальный CuttingEngine; oracle использует decimal; значения конвертируются к double по контракту API. Части имеют Quantity=1, Name=P0..Pn, Id=p0..pn, MaterialId=m; Material Id=m, Name=M, StandardLength=BarLength. Options TimeLimitSeconds=1, MaxPatternCount=10000, ToleranceMm=0.01.
- **Вход полностью:** A (n=15): BarLength=1.4, CutWidth=0.1, Lengths=[1.3,1,0.8,0.5,0.4,0.3]. B (n=133): BarLength=0.6, CutWidth=0.2, Lengths=[0.4,0.3,0.1]. C (n=134): BarLength=1.4, CutWidth=0.1, Lengths=[1.3,1.1,0.9,0.6,0.6,0.3,0.1]. Все количества 1; каждый отдельный список — отдельная задача.
- **Шаги/команда:** общая foreground-команда; Engine() random seed3030, 150 attempts; каждый исключительный вызов записан как oracleRejected с полным входом и stack trace.
- **Ожидаемое с источником:** spec строки 358, 215–219 допускают равенство Length+CutWidth=BarLength; точные десятичные 1.3+0.1=1.4 и 0.4+0.2=0.6 помещаются. B — 3 bars: [0.4], [0.3], [0.1], суммарный остаток 0.4; нижняя граница ceil(1.4/0.6)=3. C — 4 bars: [1.3], [1.1,0.1], [0.9,0.3], [0.6,0.6], все полные с учетом резов, общий остаток 0; lower bound 5.6/1.4=4.
- **Факт:** все три задачи отвергнуты **ArgumentException: Part 'P0' does not fit into a single bar. (Parameter 'task')**, Validate line143. Возвращенного решения нет; фактический count/remainder отсутствует, поэтому расхождение — ложное отклонение допустимой десятичной задачи, не неправильный вычисленный count. Oracle ожидал 4/3/4.
- **Доказательства:** `evidence-rerun.json:706–757`; `src/NStLine.Cutting/Services/CuttingEngine.cs:142–143` — строгое double-сравнение без допуска.
- **Частота:** 3/150 попыток oracle (каждый конкретный вход 1 раз в исправленном прогоне). Два из трех содержат одинаковую критическую пару 1.3+0.1. Первый исторический прогон также прервался на oracle, но его input не записан и как отдельный повтор не учитывается.
- **Влияние:** допустимые дробные размеры не рассчитываются; некорректное сообщение о геометрии.
- **Причина-гипотеза:** binary64 суммы: 1.3+0.1 округляется к 1.4000000000000001 (превышение bar около 2.220446049250313e-16 mm), 0.4+0.2 к 0.6000000000000001 (около 1.1102230246251565e-16 mm). Валидация трактует округление как реальное переполнение.
- **Уверенность:** высокая для API-факта и точной десятичной допустимости; причина соответствует исходникам, отдельный double bit-dump не делался.
- **Ограничения:** API тип double, то есть строго в binary64 такие суммы действительно больше bar; находка относится к пользовательскому смыслу десятичных миллиметров, а не к нарушению операции сравнения double. Реальный UI ввод этих списков не выполнялся. Политика допустимого числового отклонения нуждается в согласовании; fixed epsilon из QA3-04 нельзя бездумно переносить в решение этого дефекта.
